# Release notes

## v0.2（2026/11/20，分支 `v0.2`，尚未合併）

### 新增
- **主持人切換階段**：主持人畫面列出全部階段與目前位置；「前往下一階段」「回到上一階段」按鈕，切換前會再確認一次。某一類沒有題目時，該類的投票階段自動跳過，並在清單上標示「會跳過」。
- **合併**（合併階段）：勾選同一分類的 2 題以上 → 「合併」→ 選用其中一題的文字或直接改寫 → 確定。組別自動合併（例如「第 1、2 組」），合併後的題目會列出「合併自」哪幾題。
- **不同分類不能合併（T23）**：勾選到不同分類時，「合併」按鈕停用，並提示「請先把分類改成一致」。分類寫錯時，直接在題目上改分類，題目會移到正確的分類區。
- **複製到另一類（並改寫描述）（T24）**：一題同時談到兩類時，按題目旁的這個按鈕，複製出一題（組別相同、分類預設另一類、標示已改寫），再把兩題各自改寫成只講一個面向。收集階段可以用在本組的題目，合併階段可以用在所有組。合併後的題目不提供這個按鈕：要先拆回，再對其中一題使用（2026/11/23 Mike 回饋；原名「分拆」，因為和「拆回」容易混淆而改名）。
- **拆回**：合併後的題目旁有「拆回」，恢復成原本的幾題（只拆一層）。
- **刪除合併後的題目（T20）**：會詢問「拆回」（預設）或「連同原題一起刪除」。
- **合併後的已改寫（T25）**：自動判斷，之後仍可手動修改。
- 小幫手畫面在合併階段改成「全部題目、依分類分區」，下方固定一條合併工具列。

### 修改
- 規格新增決策 T23～T25，並更新 A6、B6、B8（G10～G13）、B9（2026/11/20 經 Mike 同意）。
- 修正：Firebase 會把組別存成陣列（例如 `[null, true, null, true]`），舊的寫法在跨組合併後可能把組別顯示錯（多出沒有的組）。已改成只認真的值，並加測試。
- 修正：其他人的修改即時進來時，正在打字的輸入框不會再被打斷（不移動沒有變動位置的題目）。
- 合併、拆回、刪除時先讀最新資料再寫入，而且只寫有變動的欄位，降低多人同時操作互相覆蓋的機會。

### 已知限制
- 兩位小幫手在同一秒合併到同一題時，後送出的會覆蓋先送出的（機率低；畫面會即時更新，看到異常可以拆回重做）。
- 投票、結果、XLSX、QR code 在 v0.3。主持人可以切到投票階段，但參與者目前只會看到等待畫面。
- 安全規則沒有變動，這一版**不需要重新部署規則**。

### 驗證結果
- Golden test：23／23 通過（G1～G13，加上輔助規則）
- 權限測試（emulator）：31／31 通過，新增：收集階段合併含別組題目時整筆被拒、原題不變；合併階段可以跨組合併、拆回、複製到另一類；收集階段只能複製本組的題目；分享階段不能合併
- 瀏覽器實測（本機練習環境）：主持人從「收集」切到「協力統整」；收集階段複製到另一類；合併階段勾選不同分類時被擋下並顯示原因；同類 2 題合併並改寫文字，組別顯示「第 1、2 組」、自動標示已改寫、列出來源；刪除合併題目時選「拆回」恢復 2 題；改分類後題目移到正確分區並存檔；自動存檔時游標不會跳走；手機寬度沒有左右捲動；投影畫面在合併階段自動依分類顯示
- 尚未驗證：手機實機、多位小幫手同時合併

### 安全規則與規格 B5 草案的差異（2026/11/20 經 Mike 同意，已寫回 spec.md B5）

先說明 Firebase 安全規則的兩個特性，後面三點都和它們有關：
- **權限是「按位置」給的。** 資料像資料夾：`sessions` 底下有一個個場次 `sessions/{代碼}`，每個場次底下再有 `meta`、`items`、`votes`、`participants`。規則寫在哪一層，就只開放那一層和它底下的東西；上一層、旁邊那一層都不算。
- **一次寫入要「整筆都通過」才算數。** 一次寫進很多欄位時，只要其中一個欄位不合格，整筆都會被拒絕，不會只寫進一部分。

B5 草案是以「工作坊當天」的角色為主設計的（參與者投票、小幫手輸入、主持人切階段），擁有者的管理動作只寫了改 `meta`、改單題 `items`。用 emulator 實際跑過擁有者流程後，發現下面三個缺口：

1. **擁有者看不到場次清單 → 加上「只有擁有者可以讀整個 `sessions`」**
   - 草案的讀取權限寫在 `sessions/{代碼}` 這一層：知道代碼就能讀那一個場次。但管理頁要列出「所有場次」，必須讀上一層的 `sessions`，草案在那一層沒有任何規則，所以被拒絕。
   - 比喻：每個房間都有鑰匙，但沒有人能看大樓的住戶名冊。結果擁有者只能自己記住每個代碼，才能管理場次。
   - 修正後只有擁有者能讀整份清單；其他人仍然只能用代碼讀單一場次，猜不到、也列不出別的場次（權限測試「場次清單：只有擁有者能列出所有場次」）。
2. **擁有者無法建立、匯入、刪除場次 → 加上「擁有者可以整筆寫入或刪除一個場次（以及它的 `access`）」**
   - 建立場次時，是一次寫入整個 `sessions/{代碼}`；匯入時，這一筆還包含 `votes`（選票）和 `participants`（參與者）。草案只讓擁有者寫 `meta` 和單題 `items`，而 `votes`、`participants` 只開放「本人寫自己的」，擁有者不在名單內。依照「整筆都要通過」的特性，整個建立或匯入都被拒絕。刪除場次（v0.4）也一樣。
   - 修正後擁有者可以一次寫入或刪除整個場次。這只開放給擁有者一人（T13、T22），小幫手、主持人、參與者的權限完全沒有變（權限測試「非擁有者：不能建立場次…」）。
3. **匯入舊場次時，舊的選票會被拒絕 → 選票的兩項檢查改成「擁有者匯入時不檢查」**
   - 草案對每張選票有兩項檢查，都是為了**投票當下**防止作弊：
     - `ts`（投票時間）必須等於「伺服器的現在時間」，避免有人偽造投票時間。
     - 投的題目必須「目前是 active、而且屬於同一類」，避免投給已經被合併的題目或別類的題目。
   - 但匯入的是**過去**的選票：投票時間是當天的時間，不可能等於匯入當下的「現在」；而且會後如果又合併過題目，有些選票會指向已經不是 active 的題目。只要有一張票不合格，依照「整筆都要通過」，整個匯入就失敗，會後備份就無法還原。
   - 修正後，這兩項檢查**只對擁有者**跳過，參與者投票時照樣檢查（權限測試「投票：時間不是伺服器時間失敗」「投給已合併的題目失敗」仍然通過）。匯入後，指向已合併題目的舊選票也不會影響結果，因為計票時本來就會忽略（R2～R4、G7）。
4. PIN 比對加上「`secrets` 裡必須真的有 PIN」——草案中，還沒設定 PIN 的進行中場次，任何人不輸入 PIN 就能當小幫手、主持人（空值＝空值）。
5. `meta/visibility` 只能是 private／live／demo；`meta/groupCount` 只能是 1～8。

### 已知限制
- 同一個瀏覽器的所有分頁共用同一個登入身分：在同一台電腦同時當兩組小幫手會互相覆蓋。實際使用時每位小幫手各用自己的裝置即可。
- PIN 沒有嘗試次數限制（6 位數字），內部工作坊可以接受；當天結束後換 PIN 或切回私人即可。
- 「刪除場次」在 v0.4（要先做自動備份）；合併、拆回、階段切換在 v0.2；投票、結果、XLSX、QR code 在 v0.3。
- 本機預覽的擁有者登入是測試帳號（不會跳出 Google 視窗）；正式網站用 Google 跳出視窗登入。
